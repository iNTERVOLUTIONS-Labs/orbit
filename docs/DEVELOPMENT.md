# Orbit · guía de desarrollo

Plataforma de despliegue en **Bash** para un VPS de Ubuntu 24.04 —y desde la v1.3.0 también Debian 12, con las decisiones probadas pero sin instalar todavía en una máquina Debian de verdad—: nginx + systemd + PostgreSQL + php-fpm. Un solo script (`orbit`, ~13.500 líneas, de las que ~960 son el catálogo de traducción), un instalador (`install.sh`), 32 suites de pruebas.

Lee `docs/ARCHITECTURE.md` antes de tocar nada serio: dice **por qué** está hecho así, y casi todas las decisiones raras tienen un bug detrás. `docs/WORKFLOW.md` es la versión larga de este fichero.

## Los siete principios

Si algo los rompe, se rediseña o se descarta. No se negocian.

1. **Despliega repositorios de git, y nada más.** Nunca aplicaciones que se modifican a sí mismas (WordPress, foros, paneles): el modelo de releases inmutables las borraría en el despliegue siguiente. Esta regla manda sobre las demás.
2. **Sin demonios residentes.** Un temporizador de systemd que llama a `orbit <algo>` sí vale; un proceso escuchando en un puerto, no.
3. **Si Orbit desaparece, el servidor sigue funcionando.** Todo lo que genera es estándar: vhosts, unidades, certbot, cron.
4. **Fallar antes de tocar producción.** Build en carpeta nueva, `nginx -t` antes de recargar, symlink al final.
5. **Todo legible con `cat`.** Nada binario, nada de estado oculto.
6. **Sin dependencias nuevas** salvo justificación fuerte, y añadidas a `install.sh`.
7. **Seguro por defecto.** No hay un modo inseguro más cómodo.

Corolario que ya se ha decidido dos veces: **el GUI no puede vivir en el servidor.** `orbit` se autoeleva a root y `orbit exec` ejecuta cualquier cosa; un panel web sería una shell de root mirando a internet. La interfaz es **Orbit Desktop** (repo aparte): corre en tu portátil, entra por SSH y llama a `orbit … --json`. Ver ARCHITECTURE §13.

## Cómo se trabaja aquí

```bash
make test     # las 32 suites + shellcheck. Tiene que salir en verde antes de commitear
make lint     # shellcheck -S warning
```

- Los comentarios explican **por qué**, no qué. Si escribes algo raro, di qué pasó cuando no lo era.
- Cada cambio de comportamiento lleva prueba. Cada bug arreglado lleva prueba que lo fija.
- Cada ciclo actualiza `CHANGELOG.md`, `ROADMAP.md` y la sección que toque de `docs/`.
- **Cada PR sube la versión un parche, siempre.** La versión vive en una sola línea de `orbit` (`ORBIT_VERSION="X.Y.Z"`; `install.sh` la extrae de ahí). El parche sube en uno (`1.0.1` → `1.0.2`) y **nunca pasa de 9**: tras `X.Y.9` viene `X.(Y+1).0` (`1.0.9` → `1.1.0`), y tras `X.9.9`, `(X+1).0.0`. En el mismo PR, `CHANGELOG.md` estrena la entrada de esa versión. Ver CONTRIBUTING §Versionado.
- Los mensajes de usuario van en **español**; el código y los commits, en inglés. El español es el **idioma fuente**: la clave de traducción es la propia frase, así que escribir un mensaje nuevo no obliga a traducirlo — pero las partes variables van fuera (`die "La app '%s' no existe." "$n"`), los colores como marcas (`{b}` `{r}`, nunca `${B}`) y un `%` literal como `%%`. Ver ARCHITECTURE §21.
- Nada de `git push` a `main` ni PRs sin que te lo pidan.

## Trampas de Bash que ya han costado bugs reales

Todas comprobadas ejecutándolas, no leídas en un manual. Ver ARCHITECTURE §10, §20.7 y §20.8.

**`errexit` se apaga dentro de un `&&` o un `||`, y se hereda.** Esto es lo más caro que ha pasado:

```bash
( cmd ) || manejar                    # ← cmd corre SIN errexit
( set -Eeuo pipefail; cmd ) || x      # ← tampoco: repetirlo dentro no lo reactiva
if ! ( set -Eeuo pipefail; cmd ); then # ← tampoco
ayudante() { ( set -Eeuo pipefail; "$@" ); }; ayudante cmd || x   # ← tampoco: se hereda por la llamada

set +e; ( set -Eeuo pipefail; cmd ); rc=$?; set -e   # ← la única que funciona
```

Con errexit apagado, un comando que falla a mitad sigue y anuncia un éxito que no ha ocurrido. Pasó en el menú (`orbit github` decía «conectado» con `gh` sin instalar) y en `tests/lib.sh`, donde 179 llamadas `run cmd && r=0 || r=$?` hacían que **ninguna prueba ejerciera errexit**. En las pruebas se escribe `run cmd; r=$?`.

**Y hay una hermana peor: la misma función es letal o inofensiva según cómo la llames.** Comprobado ejecutándolo en bash 5.2.21, con una `f` que dentro hace `d="$(tubería que falla)"`:

```bash
f                      # llamada directa   → muere, rc=100
_v="$(f)"              # capturada          → sobrevive, y _v trae la salida parcial
local x="$(falla)"     # declaración+asignación → nunca falla: se mira el estado de 'local'
```

O sea que un ayudante puede llevar dentro un instalador muerto y no dar la cara mientras alguien lo llame capturándolo — **y la prueba que lo ejerza capturándolo tampoco lo verá jamás**. Cuando escribas una función que asigne desde una tubería, ponle el `|| true` aunque hoy la llames de la forma que sobrevive; la línea que la llama de la otra forma se escribe sola dentro de seis meses. Y para ejercerlo en una prueba, llámala **sin capturar** dentro de un subshell con las banderas puestas.

**Cuidado también con `set -e` dentro del arnés:** `tests/lib.sh` corre con `set -uo pipefail` y **sin** errexit, así que el `set +e … set -e` del recuadro de arriba no lo restaura, lo **enciende** para todo lo que venga detrás. Pasó escribiendo esa misma prueba: la sección siguiente, que ejercía un fallo a propósito, dejó de reportar y se llevó la suite por delante.

**`pipefail` + asignación mata antes del mensaje.** `x="$(cmd | filtro)"` hereda el código de la tubería; con errexit, el `die` que explica el fallo queda inalcanzable y el usuario ve un código de salida a secas. Pasó en `orbit env list` (grep sin coincidencias) y en `orbit restore` (tar de un fichero corrupto). Cuando «no he podido» es una respuesta válida, `|| true`.

**`cmd | grep -q` bajo `pipefail` devuelve 141, no 0.** `grep -q` sale corriendo en cuanto encuentra la línea y cierra la tubería; quien escribe al otro lado recibe un SIGPIPE y muere con 141, y `pipefail` se queda con ese 141. Una condición escrita así **nunca** es cierta. Pasó en `install.sh`: la comprobación de si `orbit` trae el núcleo de idiomas fallaba siempre, y el instalador se quedaba en español para todo el mundo sin dar ningún error. Saca la salida a una variable y comprueba ahí, o usa `grep -c … >/dev/null`, que lee hasta el final.

**`while read` sin redirección lee de stdin.** Se come lo que venga detrás y la lista sale vacía. Pasó en `orbit status`: pintaba como servicios las teclas que pulsabas después en el menú.

**`\r` sin terminal no borra nada.** El spinner dejaba una línea por fotograma en cualquier log redirigido. Comprueba `[[ -t 1 ]]`.

**`ask` escribe la pregunta por stdout.** Si lo llamas dentro de algo cuya salida se captura, redirige: `ask x "..." "$def" >&2`. `choose()` devolvía la pregunta pegada a la respuesta en servidores sin fzf.

**Con `--json`, por stdout no va nada que no sea el JSON.** Ni un `✔`. Y una colección vacía significa «no hay», nunca «no he podido preguntar»: si el dato no se puede obtener, se aborta con error por stderr y stdout limpio.

**Hay caracteres que parecen texto y son emoji.** `✔` (U+2714) y `✖` (U+2716) están en `emoji-data`, así que la fuente de emoji en color se los queda: traen su propio verde —el `${GRN}` de delante no pinta nada, y `NO_COLOR` no lo apaga— y ocupan dos celdas, que descuadra todo lo alineado detrás con `%-18s`. `✓` (U+2713) y `✗` (U+2717) no están en esa lista. Y `⎇` (U+2387) no es emoji pero DejaVu Sans Mono no lo trae, así que sale un cuadrado. Los símbolos van en la tabla `G_*` de la cabecera, no escritos a mano en un `printf`.

**Dos sistemas con el mismo número de versión de la misma herramienta no son la misma herramienta.** Debian 12 y Ubuntu 24.04 traen los dos «mawk 1.3.4», y son snapshots distintos: el de Debian (`20200120`) **no entiende las expresiones de intervalo** `{40}`, el de Ubuntu (`20240123`) sí. Sólo `mawk -W version` los separa. Costó el autodespliegue entero en Debian: `_remote_head` sacaba el SHA con `awk '$1 ~ /^[0-9a-f]{40}$/'`, así que `git ls-remote` contestaba bien, Orbit no lo reconocía, y concluía «no he podido preguntar al remoto» en cada pasada — **el autodespliegue dejaba de desplegar sin un solo error**. Si necesitas una expresión de intervalo, hazla en bash (`[[ =~ ]]` usa la regex de glibc) o cuenta a mano con `length()`. Hay una prueba de clase que lo vigila en `unit_test`.

**Y hay terminales que no hablan UTF-8.** Un `LANG=C` por SSH —un VPS recién creado— convierte cada símbolo de tres bytes en tres borrones. `_ui_unicode()` lo detecta y la tabla se cae a ASCII; `UI_GLYPHS=unicode|ascii` lo fuerza. Ver ARCHITECTURE §20.9.

Además: `nullglob`, `local` en toda variable de función, `printf '%-9s'` cuenta bytes y no caracteres, y `confirm` recibe valores de campo (`no`, no `n`).

## Lo que las pruebas unitarias no ven

**Varias suites se saltan solas si falta una herramienta, y lo dicen en una línea que se pierde entre mil.** `deploy_test` necesita `rsync`, las de nginx necesitan `nginx` y `php-fpm`, y bastante más de lo que parece necesita `jq`. Sin ellos `make test` sale en verde habiendo probado **dos tercios**: 1.662 comprobaciones contra 2.447, medido apartándolos del `PATH` y no a ojo. Si vas a fiarte del verde, instálalos primero — `make test-strict` es el que se niega a mentirte.

**Y había un tercer estado, peor que los dos.** Auditando eso salió que sin `jq` no se saltaban tres bloques: se ponían **en rojo**, con 16 fallos repartidos entre Angular, el selector de scripts y el recuperador de lockfiles. Ni probado ni saltado: acusando a quien no era, y mandándote a depurar código que estaba bien. Las tres afirmaciones dejaban de ser ciertas *por diseño* —las tres funciones tienen su camino de respaldo declarado sin `jq`— y nadie lo había mirado desde fuera. Cuando escribas una prueba que dependa de una herramienta opcional, la pregunta no es sólo «¿se salta?» sino «¿qué afirma si no está?».

**Y una guarda puede existir, ser correcta de leer y medir lo que no es.** `python_test` se saltaba solo si faltaba `python3-venv`, preguntando `python3 -m venv --help` — que **contesta que sí aunque el paquete no esté**: el módulo viene en la biblioteca estándar y lo que falta es `ensurepip`, que sólo se nota al crear el entorno. Así que la guarda daba paso y la suite se ponía en rojo con 16 fallos acusando al despliegue de Python, que estaba bien. En el runner de Ubuntu era invisible, porque allí ese paquete viene puesto: hizo falta el trabajo de CI en Debian para que faltara de verdad. La guarda ahora **crea un entorno**. Regla: **preguntarle a una herramienta si existe no es preguntarle si funciona** — y si la guarda es barata de ejecutar de verdad, ejecútala.

**Y hay un cuarto estado, que es no ejecutarse.** `provision_test.sh` llevaba desde su propio commit sin que la lanzara nadie: no estaba en el `Makefile`. Son 36 comprobaciones de credenciales generadas, travesía de rutas y escritura a través de enlaces simbólicos — no lo más prescindible, precisamente. No lo vio nadie porque **el recuento del final sólo suma las suites que sí se lanzaron**: un fichero ausente de la lista no deja hueco en ningún sitio, y las otras 31 salían en verde. Y al ejecutarla apareció debajo el tercer estado de siempre: sin `jq` se ponía en rojo, porque sin `jq` no se aplica ningún descriptor y sus afirmaciones dejan de ser ciertas por diseño. Ahora `make check` cruza los `tests/*_test.sh` que hay contra los que el target `test` invoca, que es la forma de la v1.2.8 con los glifos: **se compara la clase entera, no el nombre que se te ocurra**. A las dos preguntas del párrafo de arriba les falta una tercera, y va primero: **¿la ejecuta alguien?**

**Y hay un quinto estado, que es la prueba haciendo daño de verdad.** `make test-strict` lanzado **como root** en el servidor Debian borró el vhost de una app de producción. `isolate_test` termina con un `cmd_remove tienda`, `cmd_remove` borraba el vhost por su ruta absoluta, y en esa máquina había una app llamada `tienda`. Las 32 suites en verde, 2.512 comprobaciones, 0 fallos, y una app **registrada, compilada, con su pool y su unidad vivos** a la que ya no atendía nadie. El arnés redirigía `/etc/orbit`, `/srv/apps`, systemd, `/etc/php` y las altas de usuarios —cada redirección con su incidente detrás, escrito en `tests/lib.sh`— y nginx era el único que faltaba, porque la ruta estaba escrita a pelo en cinco sitios y no había dónde desviarla. La regla: **una ruta absoluta dentro de una función que borra es una prueba esperando a que alguien la lance como root.** Y la forma de auditarlo no es leer las suites: móntales un sistema falso encima —`unshare -m`, copias montadas sobre los `/etc` que toquen, testigos plantados con los nombres de app que usan— y mira qué queda tocado. Señaló la suite culpable a la primera. Ver ARCHITECTURE §11.1.

**Y su segunda mitad, que costó la hora siguiente: ninguna de las tres preguntas que se hacen veía esa web muerta.** `nginx -t` pasa, porque lo que falta no es sintaxis sino un fichero; `orbit list` pintaba `php-fpm`, que es una **constante** escrita para las apps PHP y no puede acusar a nadie; y `orbit doctor` salía entero en verde. El visitante recibía la conexión cerrada del servidor por defecto —ni 404 ni 502, `curl` dice `000`—. Es §23.6b otra vez: **¿esta fuente sabe de verdad lo que le estoy preguntando?**, y aquí la respuesta era que ninguna de las tres lo sabía. Cuando una columna de un listado no puede tomar más de un valor, no es un estado: es una etiqueta.

**Y una prueba puede necesitar privilegios, no sólo herramientas.** `php-fpm` **sólo baja de usuario si lo arranca root**: lanzado por un usuario normal ignora en silencio la directiva `user` de cada pool y todos corren como quien lo lanzó. La prueba del aislamiento entre apps PHP necesita dos pools con usuarios distintos, así que en CI —que corre como `runner`— salía en rojo acusando a código sano: el tercer estado otra vez, ahora por una capacidad y no por un binario. Pide el privilegio explícitamente y, si no lo hay, sáltala diciéndolo. Y compruébalo **ejecutando los tres caminos** (root, no-root con sudo, sin nada), porque el que falla nunca es el que tienes delante.

**Y el primer contacto con un servidor de verdad costó cinco minutos y dos bugs.** Una imagen de Ubuntu con `Suites: noble` a secas —sin `-updates` ni `-security`— dejaba `build-essential` sin resolver, y `install.sh` lo contaba como «held broken packages» y un número de línea: nueve `apt-get install` con `-qq` y la salida a `/dev/null` escondían justo el dato que hacía falta. Ninguna prueba podía verlo porque ninguna instalaba nada. La lección no es sobre apt: **si silencias una orden, encárgate de que su fallo se oiga igual** — y si hay nueve iguales, el sitio del arreglo es uno.

**Probar de punta a punta encontró bugs en los cuatro modos, con 1.258 comprobaciones en verde.** EVA: 4. Sencillo: 1. Menú: 3. JSON: 3. Si tocas algo, ejecútalo de verdad: repo git real, build real, nginx real, y consúmelo como lo haría quien lo usa.

**Ya se ha probado una app con proceso en un VPS de verdad, y salieron cuatro fallos que ninguna suite podía ver.** Next con corepack, dominio real detrás de Cloudflare, certbot de verdad. Se ejercitaron la unidad de systemd, `health_wait`, el rollback automático, el reinicio sin corte bajo tráfico, el aislamiento por app, el vigilante, el autodespliegue, certbot y el ciclo de copia y restauración con base de datos. Lo que salió:

- **El reinicio «sin corte» daba 1-2 respuestas 502 por despliegue.** `systemctl reload nginx` vuelve cuando entrega la señal, no cuando el cambio está aplicado, y Orbit paraba el proceso viejo **10 ms** después. Lo que iba en vuelo hacia ese puerto moría con él.
- **Los certificados se emitían pero no podían renovarse jamás.** La redirección a HTTPS es un `if` de `server`, y nginx corre esa fase **antes** de elegir el `location`, así que se llevaba por delante el reto de ACME. La emisión funciona porque cuando se emite todavía no hay redirección: el fallo sólo existe a partir del segundo intento, y el certificado caduca en silencio a los 90 días.
- **Tras un primer despliegue fallido, Orbit decía «esto no es tu código» cuando sí lo era**, y mandaba a `nginx -t`. Miraba sólo el symlink, y una release que compila y se estrella deja el mismo rastro que un vhost roto.
- **Cuatro mensajes sacaban un `\n` literal por pantalla**, en los dos idiomas.

**Y la lección de método, que costó una hora: la primera medición se acusó a sí misma.** La sonda de tráfico iba a ~100 req/s, por encima del `limit_req` de 40 r/s del vhost, así que nginx devolvía 503 y parecía un corte del despliegue. El bug estaba en la sonda. Lo mismo de los dobles de prueba, pero en un servidor: **antes de creerte una medición, comprueba qué marca en reposo.** Y tres veces seguidas cayó lo mismo por otro lado — `pgrep -f 'worker process'` y `pkill -f '<patrón>'` **se encuentran a sí mismos**, porque el patrón está escrito en la línea de órdenes del propio shell; una vez mató la sesión a mitad de prueba. `ps -C` compara el ejecutable y no tiene ese problema. Y `kill -0` sobre un proceso de otro usuario contesta «permiso denegado», que en bash es el mismo falso que «no existe»: una espera construida sobre eso da por terminado siempre.

**Y ya están los seis stacks con proceso**, cada uno con su fallo. Django: `ALLOWED_HOSTS = ['*']` daba un aviso falso en cada despliegue porque la lista se dividía sin comillas y el `*` se expandía con los ficheros del directorio. Laravel trajo tres —las cachés de artisan corrían como `deploy` sobre una release del usuario de la app (**no se podía desplegar en absoluto** con el aislamiento puesto), `_env_write` le robaba el `.env` al usuario de la app, y `orbit new --db` escribía una `DATABASE_URL` que Laravel no lee y dejaba la web en 500. Go destapó que `~/.cache` se creaba de **root** —`install -d -o X a/b/c` sólo le pone dueño al último componente— así que tampoco se podía desplegar; Node no se enteraba porque Orbit le crea la ruta entera de corepack, y Deno se libró porque su `DENO_DIR` vive fuera de `.cache`. Bun y Deno salieron limpios.

**El patrón de los cuatro últimos merece leerse junto:** todos son del refactor del aislamiento (§5.3), y todos son el mismo descuido —un sitio que siguió usando el usuario de antes— en un rincón distinto. Cuando cambies quién ejecuta algo, la pregunta no es «¿he cambiado la función?» sino **«¿quién más escribía en lo que ahora es de otro?»**. Y la suite no podía verlo porque doblaba `as_deploy` y `as_app` al mismo shell: ahora apuntan **quién** habría corrido cada cosa.

**Y la máquina ya se ha reiniciado de verdad: vuelve sola.** 34 comprobaciones sobre el servidor recién arrancado (`/root/COMPROBAR-TRAS-REINICIO.sh`), 0 fallos y **cero intervención** — las 5 apps con proceso, nginx, php-fpm con sus 6 pools y los 11 sitios sirviendo. Orbit no participa en el arranque: no hay nada suyo ahí, vuelve lo que systemd tenía apuntado, y el `enable` de cada unidad se reafirma en cada despliegue. Lo que hasta ahora estaba probado era la mitad barata —parar todo y levantarlo desde una sesión que vive en esa máquina—, y conviene saber qué se saltaba: el orden real del arranque, las dependencias que en frío aún no están, y si la máquina vuelve siquiera. `systemd-analyze verify` valida la sintaxis de la unidad y no dice nada de eso. Ver ARCHITECTURE §5.5.

**Dos apuntes de método salidos de repetir esa misma prueba**, y los dos valen para cualquier medición sobre una máquina viva. El primero: **una comprobación a los dos minutos del arranque no dice lo que parece.** Con `Restart=always`, una app que arranca y se muere en bucle da `is-active` igual que una sana; lo que las separa es el **contador de reinicios**, y por eso se repitió la pasada a las dos horas — sigue en 0. El segundo: **el inventario del script decía «8 sitios» y son 11.** El número venía arrastrado de la tanda anterior, y no cuadraba con su propio total (3+10+6+11+2+2 = 34), que es la clase de dato que sobrevive a tres revisiones porque nadie suma la columna.

**Queda sin medir el reinicio a mitad de despliegue**, pero auditarlo ya no deja razonamiento entero: son tres residuos, y sólo uno era un agujero. La release a medio construir no llega a `current`; la unidad puente ni se hace `enable` ni se retira sin oír antes a la canónica; y el **testigo de mantenimiento** sí sobrevive al arranque, porque en el arranque no corre nada de Orbit. Con un `reboot` ordenado no pasa nada —**bash ejecuta la trampa `EXIT` también cuando lo mata un SIGTERM**, comprobado ejecutándolo y contrario a lo que se diría de memoria—, así que el residuo sólo existe sin SIGTERM: `reboot -f`, corte de luz, SIGKILL por `TimeoutStopSec`. Lo que faltaba no era el arreglo sino el aviso, otra vez: `orbit doctor` contaba el `php artisan down` de Laravel y se callaba el mantenimiento propio. Ya lo dice, y **sin acción**, porque levantar una web que alguien bajó a propósito es peor que dejarla bajada.

**Dos cosas del entorno que no son de Orbit pero cuestan una hora:** Orbit **no instala** los toolchains de Go, Bun ni Deno a propósito (§18.6), así que hay que ponerlos donde los vea el `PATH` de las unidades (`/usr/local/bin`); y el binario por defecto de Bun **muere con SIGILL** en un Xeon sin AVX2 — hace falta su build `baseline`.

**Y un residuo, ya arreglado, que enseña dónde mirar:** un autodespliegue fallido deja `orbit-autodeploy.service` en `failed`, y eso es **deliberado** —es el aviso de que el automático no funciona, y la pasada siguiente lo pone en verde sola—. Lo que fallaba era el silencio alrededor: `systemctl is-system-running` pasa a decir «degraded», que es lo que mira media monitorización, y `orbit doctor` no lo mencionaba; y al retirar el temporizador ya no hay pasada siguiente, así que ese `failed` se quedaba para siempre. Ahora doctor lo cuenta **sin arreglarlo** —apagar la alarma no es apagar el fuego— y `autodeploy disable` sí lo limpia, porque ahí ya no queda nada que pueda ponerlo en verde.

**Y de ahí salió el primer fallo llegado de un servidor de verdad**: `ProtectHome=true` tapa `/home` con un tmpfs en modo 000, así que el `HOME` que systemd deduce de `User=deploy` no se podía ni abrir y una app de Node con corepack compilaba bien y reiniciaba en bucle. Ninguna prueba lo alcanzaba —el build corre con `sudo -u deploy -H`, fuera del cajón— y ninguna miraba la unidad generada. Ahora hay `tests/systemd_test.sh`, pero la lección es la de arriba: **lo que sólo existe dentro del espacio de nombres de systemd no lo ve `make test`**. Para comprobar algo así, móntalo: `unshare -m` con un tmpfs en modo 000 sobre `/home` y el proceso corriendo como no-root reproduce el `EACCES` exacto. Ver ARCHITECTURE §5.1.

**Y la primera instalación entera en Debian encontró un fallo que llevaba ahí desde siempre, también en Ubuntu.** El paso 12 hacía `ufw allow OpenSSH`, y ese perfil miente dos veces. La primera es ruidosa: **no existe si no está instalado `openssh-server`** —el paquete lo trae, en las dos distribuciones—, así que en una máquina sin él ufw da error y `errexit` mata el instalador en el paso 12 de 13, sin llegar a instalar `orbit`. La segunda es la cara: el perfil declara **`ports=22/tcp` a pelo**, así que un servidor con sshd en otro puerto recibía un cortafuegos que abre el 22 y **tapa el suyo** — sin un solo error, anunciando «UFW activo: sólo SSH, 80 y 443», y con la sesión abierta sobreviviendo porque ufw deja pasar lo ESTABLECIDO. Te enteras al reconectar. La regla que queda: **un perfil de aplicación describe el paquete, no tu configuración**; si abres un puerto en el cortafuegos, pregúntale al servicio en cuál está de verdad. Y para medirlo hace falta un cliente en otro espacio de red: desde localhost ufw deja pasar `lo` entero y todo parece abierto siempre. Ver ARCHITECTURE §23.6.

**Y la máquina Debian ya se ha reiniciado: vuelve sola.** 14 comprobaciones sobre el arranque en frío, 0 fallos y cero intervención — los seis servicios base, el cortafuegos, la app con proceso con `NRestarts=0` y su web contestando 200. De ahí salió la lección de método: **el instrumento no puede formar parte de lo que mide.** La comprobación estaba enganchada a `multi-user.target`, o sea que formaba parte del arranque, así que mientras corría el arranque no podía estar terminado y `systemctl is-system-running` contestaba `starting` — y `systemd-analyze blame` la ponía la primera de todas con 46 s, que eran su propio `sleep`. Se saca con un temporizador `OnBootSec`. Es la sonda de tráfico de §5.2 en otro plano (allí la medición se pasaba del `limit_req` y se acusaba a sí misma; aquí se acusa por existir), y el mismo día el mismo script se había cazado a sí mismo con un glob `orbit-*.service` que incluía su propia unidad. Ver ARCHITECTURE §5.5.

**Y de la misma tanda salieron tres informes que preguntaban a quien no era.** `orbit status` decía `○ ufw (inactive)` con el cortafuegos filtrando: `ufw enable` carga las reglas en el kernel al momento y deja la unidad habilitada para el arranque siguiente **sin arrancarla**, así que `systemctl is-active ufw` miente hasta el primer reinicio — o sea justo después de instalar, que es cuando más se mira. `orbit doctor` salía entero en verde con una app parada y su web dando 502, mientras `orbit list` sí decía `stopped`: **el dato existía y no estaba donde se pregunta «¿qué va mal?»**. Y `confirm` hacía `read -r a || true`, así que no distinguía «el usuario pulsó Enter» de «no había usuario» — con un valor por defecto que sea «sí», eso es una decisión tomada por nadie, y en `orbit new` llegaba a lanzar la emisión de un certificado de Let's Encrypt y a devolver 1 sobre una app creada, desplegada y sirviendo. Los tres son la misma pregunta: **¿esta fuente sabe de verdad lo que le estoy preguntando?** Y el `ufw` trae cola: la comparación es contra su texto, y ufw traduce su salida, así que va con `LC_ALL=C` o un servidor en otra lengua contesta que no.

**Del arreglo de `confirm` salió otra lección, porque el primer intento estaba mal.** Miraba `! -t 0` —«no hay terminal»— y **una tubería tampoco es un terminal y sí trae respuesta**: `echo n | orbit …` dejó de contestar que no. Lo cazó la suite, no yo. Lo que separa «alguien ha contestado» de «no había nadie» no es de dónde viene la entrada sino si `read` **consigue leer algo**; y ojo, porque `read` devuelve 1 también cuando lee una línea sin salto final (`printf n | …`), donde sí ha contestado alguien. Regla: **`-t 0` responde «¿hay un humano interactivo?», que casi nunca es la pregunta; la pregunta suele ser «¿hay datos?».**

**Y desplegar la primera app con proceso destapó media regla en `detect_stack`.** La rama que atrapa «servidor de Node sin framework» exigía «tiene `start` y **no** tiene `build`». Un servidor en TypeScript tiene las dos cosas, así que caía al `else` y salía `static` con `A_OUTDIR='dist'` — y ahí **no salta ni el aviso de la carpeta que no existe, porque `tsc` la crea**: nginx publica el servidor compilado y la app no se arranca nunca. La rama de `express`, tres líneas más arriba, ya lo hacía bien. Es el agujero de §18.8 otra vez, entrando por la mitad que la guarda no cubría: **tener un paso de build no dice que seas un sitio estático** —lo tienen casi todos los servidores compilados—, tener `start` sí dice que hay algo que arrancar. Cuando escribas una guarda con un «y no», pregúntate qué entra por la puerta que ese «y no» deja abierta.

**Y la última tanda dejó una lección sobre qué se puede leer de un `.env`.** El aviso de «esta app encola y no hay quien lo ejecute» llevaba tiempo escrito y **callado en el único servidor donde había una cola de verdad**: leía `QUEUE_CONNECTION` del `.env` y, al no encontrarla, concluía que no había cola. Pero desde **Laravel 11 el valor por defecto del framework es `database`**, no `sync` — y el `.env` que crea Orbit no trae la clave, porque el esqueleto de Laravel tampoco. O sea que la condición era exactamente del revés en el caso más común. Lo encontró desplegar un Laravel 13 y mirar `config/queue.php`, no una revisión. La regla que queda: **una clave ausente en un `.env` no es un «no», es «pregúntale al framework»** — y el sitio donde preguntar es el valor por defecto que declara su propio config. Y su hermana, que apareció midiendo lo mismo: con `config:cache` —que Orbit ejecuta en cada despliegue— **Laravel no lee el `.env` en tiempo de ejecución**, así que un `orbit env set` no cambia nada hasta el despliegue siguiente. Las dos veces el fallo estaba en creerse una fuente sin comprobar quién la lee de verdad.

**Ningún stack tiene que estar ya en la raíz** (§18.9b). Y la forma importa más que el resultado: `detect_stack` **se llama a sí misma** sobre la subcarpeta y una sola función traduce las coordenadas después, en vez de que cada rama componga sus rutas. Son dieciséis ramas y crecen, y la que se olvidara fallaría *hacia servir la carpeta equivocada*. Si añades un stack, no tienes que pensar en monorepos.

**Y de ahí, la lección de colocación:** la primera versión puso la búsqueda delante de la rama de `package.json`, con un razonamiento correcto sobre workspaces que resultó falso para todo lo demás — de paso se adelantaba a `composer.json`, `requirements.txt` e `index.html`, y un sitio estático con un `tools/pyproject.toml` al lado pasaba a ser una app de Python. **Lo que hay en la raíz es el repositorio**; sólo cuando la raíz no reconoce nada tiene sentido mirar dentro. Lo encontró probarlo con repositorios de mentira, no leerlo.

**Un patrón que ya ha costado ocho agujeros, y que conviene tener delante al meter un stack nuevo:** la rama de repuesto de `detect_stack` deja `A_TYPE=static` con `A_OUTDIR="."`, o sea nginx sirviendo la raíz del repositorio. Para un sitio que es HTML es lo correcto; para cualquier otra cosa, el modo de fallo por defecto es **enseñar el código fuente**. Ahí caían Deno, Bun y hasta un servidor de Node sin framework. Ante la duda, con proceso: un despliegue que falla en voz alta es mucho mejor que uno que sale bien y publica el `.env`. Hoy esa rama avisa de lo que va a hacer, pero **la regla sigue siendo tuya**: cuando añadas un stack, la primera prueba que hay que escribir es qué pasa cuando no coincide nada.

Y la lección de segundo orden, que salió de revisar Deno y Bun **después** de darlos por terminados con las pruebas en verde: una revisión adversarial encontró cuatro caminos más al mismo agujero. Con Laravel se repitió: dos revisiones encontraron una ejecución de código como root en cada despliegue, el snippet de seguridad apagado justo donde el nombre del fichero lo elige un desconocido, y un `orbit new` que se moría en silencio. **Verde no es hecho.** Si el cambio toca detección, nginx o el `.env`, dale a otro par de ojos el encargo explícito de romperlo, y con lentes distintas: una para la detección, otra para el modelo de despliegue.

**Y hay cosas que sólo se ven ejecutando el producto entero.** El health check de Laravel lo escribí, lo probé con un servidor HTTP de verdad y salió verde — y al desplegar un Laravel de verdad resultó que **php-fpm seguía sirviendo la release anterior** (caché de `realpath`, 120 s), así que la comprobación medía la release que ya estaba y daba por buena una rota. Ninguna prueba unitaria podía verlo: el fallo vive en la interacción entre el symlink, php-fpm y el tiempo. Cuando toques el despliegue, rómpelo a propósito y míralo con `curl`.

**Y desconfía de tus dobles de prueba.** El `artisan` falso de `deploy_test` era un fichero vacío que salía con 0: se podían borrar los tres pasos de Laravel uno a uno y `make test` seguía en verde. Una prueba construida sobre un doble que no puede fallar no comprueba nada. Cuando escribas un doble, la primera pregunta es qué mutación del código de verdad tiene que ponerlo en rojo — y luego ejecútala.
